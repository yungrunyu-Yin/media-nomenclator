# 架构

MediaNomenclator 把「整理媒体库」拆成一条**可控、可中断、可验证**的流水线。
本文说明各层的职责与数据流向。

---

## 1. 分层

```text
┌─────────────────────────────────────────────────────────────────┐
│  Skill 层   skills/media-library-auto-rename/                   │
│  · SKILL.md                流程、规则、安全约束（给 AI 助手读）  │
│  · naming-config.json      规则配置（给人和程序读）              │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 按规则驱动
┌───────────────────────────▼─────────────────────────────────────┐
│  规则层     src/naming/                                         │
│  · techinfo_reorder.py     技术信息字段规范化                    │
│  · 命名模板 / 语言口径 / 目录规则 / 字幕策略（配置驱动）          │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 需要元数据时
┌───────────────────────────▼─────────────────────────────────────┐
│  数据源层   src/sources/                                        │
│  · tmdb/tmdb_api.py        作品身份 / 季结构 / 分集标题 / 别名   │
│  · （计划）dandanplay、其他源   统一 search/detail/season 接口    │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 产出重命名计划
┌───────────────────────────▼─────────────────────────────────────┐
│  计划层     计划 JSON（mkdir / rename / move）                   │
│  · v2_plan.py 生成    · check_plan.py 体检    · snapshot.py 快照 │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 用户确认后执行
┌───────────────────────────▼─────────────────────────────────────┐
│  存储层     src/storage/                                        │
│  · cd2/            CloudDrive2 gRPC 后端 + 计划执行器 + 只读审计  │
│  · （计划）本地文件系统 / 网盘 MCP 后端                          │
└─────────────────────────────────────────────────────────────────┘
```

**关键设计**：规则层与存储层**完全解耦**。同一套命名规则，换后端只换 I/O 通道，
规则、季集判定、字幕策略、技术信息策略一律不变。

## 2. 处理流程

```text
Step 1  扫描
        ├─ 列出视频、外挂字幕、子目录
        └─ 分页必须翻到底（条数=页大小 就还有下一页）

Step 2  建立视频—字幕对应关系
        ├─ 按基名分组，要求每组 = {视频扩展名, 字幕扩展名}
        └─ 落单 / 多余 → NEED_REVIEW

Step 3  识别作品
        └─ 媒体类型 / 片名 / 年份 / 季数 / 集数

Step 4  查询数据源                     ← 主来源 + 补充来源，按字段分层采信
        ├─ 作品身份、季结构、季名
        ├─ 分集标题（排除占位编号与站点自拟描述）
        └─ 中文译名的独立印证

Step 5  确定集标题
        └─ 可靠中文 → 可靠英文 → 省略（禁止机翻与自拟）

Step 6  读取技术信息
        └─ 剧集不写 / 电影只写分辨率；读不到不补猜

Step 7  生成计划                       ← OLD → NEW 对照 + Dry Run
        └─ 用户确认 ──┐
                      ▼
Step 8  执行（分批）  →  Step 9  校验（重新列目录 + 内容快照比对）
```

---

## 3. 为什么把「计划」单独抽出来

直接对文件系统或云盘发一连串改名请求，有三个问题：不可预览、不可中断、不可审计。

因此本项目统一走**计划文件**：

```jsonc
{
  "name": "Example Show",
  "api_root": "/media/anime/Example-Show",
  "operations": [
    {"op": "mkdir",  "parent": "...", "name": "第2季"},
    {"op": "rename", "path": "...", "new_name": "..."},
    {"op": "move",   "paths": ["..."], "dest": "..."}
  ],
  "verify": { "must_exist": [...], "must_not_exist": [...], "expect_file_count": 24 }
}
```

带来的好处：

- **可预览**：执行器默认只打印，什么都不改。
- **可审计**：计划是可读 JSON，可逐条人工过目，也可用 `check_plan.py` 机器体检。
- **可重试**：执行器幂等 —— 已完成的条目重跑会自动跳过，限流中断后直接重跑即可。
- **可验证**：计划自带 `verify` 断言，执行后重新列目录校验。

## 4. 安全机制的位置

| 机制 | 落在哪一层 |
|---|---|
| 不覆盖 | 执行器预检：目标存在即 `SKIPPED_CONFLICT`；移动固定 `conflictPolicy=skip` |
| 不猜 | 规则层：无法确认即 `NEED_REVIEW`，不进计划 |
| 不落挂载盘 | 执行器硬护栏：计划里出现盘符 / 反斜杠 / UNC 直接中止 |
| 不删视频 | 客户端与执行器**不含**删除 API；删除能力被隔离在独立脚本，且只接受字幕或空目录 |
| 幂等 | 执行器：源已消失但目标已存在 → `SKIP(已完成)` |
| 限流韧性 | 执行器：分批 + 退避重试；限流错误分类识别 |
| 内容未变 | `snapshot.py`：名字 + 字节数 + MD5 多重集比对 |
| 密钥不外泄 | 数据源与存储层：只从环境变量 / 独立文件读取，只回显掩码 |

## 5. 存储后端对比

| 后端 | 状态 | 说明 |
|---|---|---|
| 本地文件系统 / Alist 挂载 | 已实现 | 直接文件系统操作 |
| **CloudDrive2 gRPC API** | 已实现 | 直连网盘原生 rename / move / mkdir，绕过 WinFsp 挂载开销；端口自动探测；目录缓存需 `forceRefresh` |
| 网盘 MCP | 已实现 | 走 MCP 接口扫描与重命名 |
| 其他云盘原生 API | 计划中 | 目标：与 CloudDrive2 后端同级的适配器 |

后端只要满足 `list / stat / mkdir / rename / move` 五个动作，就能接入现有执行器 ——
`apply_plan.py` 的动作集合刻意与后端能力一一对应。

## 6. 扩展点

### 新增一个数据源

需要提供等价于以下四项的能力，并保证**只读**：

| 能力 | 用途 |
|---|---|
| `search` | 由片名/剧名找候选条目 |
| `detail` | 取作品身份、年份 |
| `seasons` | 取季结构（季号 / 季名 / 该季首播年 / 集数） |
| `episodes` | 取某季全部分集标题 |

还需遵守两条纪律：**密钥不入库不入配置**；**失败时给出降级说明**而不是静默编造。

计划中的 dandanplay 适配器即按此约定设计。

### 新增一种媒体类型

在配置里增加该类型的命名模板与技术信息策略，并在规则层加入对应的识别逻辑。
规则引擎本身与媒体类型无关，但目前只实现了影视类规则集。

### 新增一个命名规则

优先改 `naming-config.json`，而不是改代码 —— 语言口径、年份口径、季集格式、
集标题链条、技术字段、目录结构、字幕策略均已外置为配置项。
