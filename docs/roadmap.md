# 路线图

本文说明 MediaNomenclator 的演进方向。**已实现的部分见 README 的「当前已实现的能力」一节** ——
本文件只写尚未完成的工作。

推进方式：**先出一部作品的 Dry Run 验收，满意后再逐部推进**，不做一次性全库改造。

---

## 近期

> **起点**：本项目的直接动因是下游的弹幕匹配（详见 README「背景与动机」）。
> 下游服务按**文件名**解析作品名与季集来匹配弹幕，因此「命名到底改对了没有」的最终判据，
> 是下游能否稳定命中正确的剧集 —— 而不是文件名字符串本身有多漂亮。

### 1. 接入 dandanplay 数据源

| 步骤 | 内容 |
|---|---|
| 1 | 申请 dandanplay 开放 API 权限 |
| 2 | 实现只读适配器，遵守 `docs/data-sources.md` §5.5 的六条约定 |
| 3 | 提供 `selftest`，一条命令判断通道可用性 |
| 4 | 在动漫类别上把主来源由 TMDB 切为 dandanplay，TMDB 等降为补充 |
| 5 | 与现有库逐部比对季集结构与分集标题，差异先出 Dry Run 交用户拍板 |
| 6 | 先试点一部动漫验收，再逐部推进 |

**边界**：只做作品识别与剧集匹配两件事，不涉及弹幕、播放、账号或社区功能。

### 2. 数据源适配器插件化

- 统一接口：`search` / `detail` / `seasons` / `episodes`
- 统一凭据读取与掩码回显
- 统一失败降级语义（不可达时给明确说明，而不是静默编造）
- 目标：新增数据源 = 新增一个适配器文件

### 3. 换源 / 换版本的差异比对工具

换数据源、或同一作品存在多个版本时，先产出**差异报告**（季集结构、分集标题），
再由用户决定是否改动。目前这类比对靠人工，工具化后可以显著降低误改风险。

## 中期

### 4. 规则集扩展到更多媒体类型

命名规则引擎本身与媒体类型无关，但目前只实现了影视类规则集（电影 / 剧集 / 动漫 / 纪录片 / 综艺）。
后续可为其他媒体类型补规则集 —— 需要先明确该类型的「作品身份」如何界定、季集概念是否存在。

### 5. 存储后端补全

把本地文件系统与网盘 MCP 整理成与 CloudDrive2 后端**同级**的适配器，
统一 `list / stat / mkdir / rename / move` 五动作接口，让执行器完全后端无关。

### 6. 测试与样例补全

| 项目 | 现状 | 目标 |
|---|---|---|
| `techinfo_reorder.py` | 有内置自测 | 转为正式单测 |
| 占位标题识别 | 有 9 条用例 | 转为正式单测 |
| 计划生成 / 体检 | 依赖真实后端 | 用假后端补可离线运行的测试 |
| 端到端示例 | 有计划格式示例 | 补一个可离线跑的完整示例 |

### 7. 交互式确认流程

目前 Dry Run 以文本摘要呈现、由用户阅读后确认。后续可提供结构化确认界面，
把 `NEED_REVIEW` / `SKIPPED_CONFLICT` 逐条摊开供勾选。

## 长期（并且刻意不做）

以下方向**不是**本项目目标，列出来是为了避免误解：

| 不做的事 | 原因 |
|---|---|
| 生成 NFO / 海报 / 缩略图 | 那是**刮削器**的工作。本项目只负责把名字改对，让刮削器自己去刮 |
| 视频转码 / 压缩 / 合并 / 剪辑 / 时间轴修正 | 只改名字，不碰内容 —— 这是安全底线 |
| 资源下载 / 索引 / 分享 | 与「整理」无关，且涉及版权 |
| 内置受版权保护的元数据 | 只读取公开元数据接口 |

## 已知的工程债

诚实记录当前的问题，便于后续处理：

1. **存储后端能力不齐**：CloudDrive2 后端最完整（含自检、审计、快照工具），
   本地与网盘 MCP 后端只有基本操作，缺少等价的审计工具。
2. **规则引擎未完全数据化**：命名格式（模板、引号、序数）已在配置里，
   但「识别」环节（从文件名解析出作品/季/集）的部分逻辑仍写在脚本中。
3. **失败恢复依赖人工判断**：限流中断后可重跑（执行器幂等），但重跑前仍需人工核实真实进度。
4. **尚无 CI**：仓库目前没有自动化测试流水线。
5. **`src/storage/cd2/` 的 proto 生成物需要手动重编译**（proto 版本升级时）。
