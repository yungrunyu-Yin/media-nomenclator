# MediaNomenclator

项目名 MediaNomenclator，仓库名 `media-nomenclator`，MIT 许可。

这是个整理媒体库文件名的工具集：认出作品、取回元数据、把文件名规范化、重命名视频，顺带把外挂字幕改成同名配对。能力以 Skill 的形式组织（AI 助手可以直接加载执行），另有一批能独立跑的 Python 脚本。

所有规则都从属于一条：**信息确认不了就不动手。**

拿不准的项保持原样，标 `NEED_REVIEW`；目标名已存在就标 `SKIPPED_CONFLICT`。两种情况下都不会用猜测去填满文件名。

## 背景与动机

这工具是被一个很具体的问题逼出来的。

为了让本地媒体库有弹幕，我部署了 [danmu_api](https://github.com/huangxd-/danmu_api) —— 一个自己搭的弹幕 API 服务器，接口兼容弹弹play 规范。它的匹配接口要从**文件名里**读出作品名、季号、集号，拿这些做标题比对和季集解析，再定位到某一集去取弹幕。

也就是说，文件名的规范程度直接决定它能不能匹配上。我这边遇到的失配大致是这几类：

- 文件名里塞着发布组、字幕组、分辨率、编码，标题被点号切得看不出边界；
- 同一部作品在文件名里写成英文名、拼音或别名，跟匹配方的标题对不上；
- 季号集号写法各异 —— `1x01`、`EP01`、`第01集`、`S1E1`，有的干脆没有集号；
- 续集被当成独立作品命名，季号从 S01 重新开始；
- 外挂字幕带着各种语言后缀，跟视频配不上对。

结果是弹幕取不到，或者取到的不是那一集的。一部剧几十集，手工改名不现实，也容易改错；改名一旦撞车或者覆盖，原文件可能就找不回来了。

所以先做这件事：把名字弄对，后面的匹配才有基础。

动漫最容易出问题 —— 别名多，季集划分在不同资料库之间也常常不一致。因此我计划接入 dandanplay 开放 API，作为动漫作品识别与剧集匹配的数据源之一，多一路判断依据来提高动漫文件命名的准确率，让下游弹幕匹配落在正确的剧集上。

有一点要讲清楚：**这个项目不获取、不存储也不分发弹幕**，仓库里没有任何弹幕数据。它只把文件**名**整理规范，好让按名字匹配的下游服务能用得上。弹幕怎么抓、怎么发，是下游服务自己的事。

| | |
|---|---|
| ✅ 负责 | 媒体文件识别；元数据获取与整理；文件名规范化；视频重命名；字幕与伴随文件同步改名；目录结构规范化 |

## 核心功能

| 能力 | 说明 |
|---|---|
| 媒体文件识别 | 从文件名和目录名认出作品、类型（电影 / 剧集 / 动漫 / 纪录片 / 综艺）、年份、季数、集数 |
| 元数据获取与整理 | 从外部数据源取作品身份、季结构、季名、分集标题、地区译名，按可信度分层采信 |
| 文件名规范化 | 统一字段顺序、分隔符、大小写和标点；去掉发布组和冗余标记；处理非法字符 |
| 视频重命名 | 按统一模板改名，保留原始容器扩展名，不转码 |
| 字幕与伴随文件同步 | 外挂字幕按同基名配对；多语言字幕按策略取舍；内封字幕只探测不改动 |
| 分类型用不同规则 | 电影和剧集 / 动漫的命名模板、技术信息策略、目录结构各不相同，全部由配置驱动 |
| 数据源可替换 | 数据源做成适配器，主来源可以按媒体类别切换 |
| 产出下游可解析的文件名 | 输出形如 `剧名.年份.SxxExx.「集标题」.扩展名`，便于下游按「标题 + 季集」解析 |
| 存储后端可切换 | 本地目录、Alist 挂载、网盘 MCP、CloudDrive2 gRPC API —— 命名规则不随后端改变 |

## 目前已经能做什么

以下都在真实媒体库上跑通过，仓库里的脚本可以直接运行。

1. **配置驱动的命名规则引擎**，一套规则覆盖电影、剧集、动漫、纪录片、综艺。语言口径、年份口径、季集格式、集标题链条、技术信息策略、目录结构、字幕策略都在配置文件里，改配置就能改行为。

2. **中文译名优先的语言策略**。剧名和集标题都先查中文译名，可靠来源能确认就用中文，确认不了才退回官方原名。不接受机器翻译，也不自己拟译名。

3. **季集识别与多季、续集判定**。季数和季名依据数据源条目的季结构来定，不靠文件名猜。两类易错情形都处理了：续集其实是同一部剧的新季；同名作品分属不同条目。

4. **集标题获取，含假标题识别**。按来源优先级取第一个真正给出集标题的来源。会自动排除两类假货：占位编号（`第1集`、`Episode 1`）和聚合站自拟的分集描述。确实找不到可靠标题就省略这一段，不硬填。

5. **TMDB 数据源适配器**（已实现）。只读 API v3 通道，一次调用就能取回完整季结构和全部集标题。内置占位标题识别、密钥掩码回显，以及针对 DNS 污染的 DoH 绕行 —— 固定真实 IP 配正确 SNI，证书照常校验，不关 verify。

6. **目录规范化**。作品主文件夹改成作品正式片名，不带年份；季文件夹统一成 `第X季`；单季作品不额外套一层季目录；番外和特别篇类目录整体跳过。

7. **外挂字幕同步**。字幕与视频按同基名配对，用「成对核对法」校验一一对应关系。内嵌字幕与多语言同名字幕的冲突不自动处理，标出来交人看。

8. **安全执行链路**。生成计划（dry-run）→ 计划体检 → 用户确认 → 分批执行 → 重新列目录校验 → 内容完整性快照比对。执行器带后端无关的路径护栏、冲突跳过策略和限流退避重试。

9. **内容完整性证明**。`snapshot.py` 记下每个文件的「名字 + 字节数 + MD5」，整理前后比一次，就能证明只改了名、内容一个字节没动。

10. **多个存储后端**。本地目录 / Alist 挂载、CloudDrive2 gRPC API 直连（绕过挂载盘的 WinFsp 开销）、网盘类 MCP 接口，三者共用同一套命名规则。

## Skill 与模块

### `skills/media-library-auto-rename/` —— 核心能力包

主体能力做成了一份 Skill：一份面向 AI 助手的操作规范 `SKILL.md`，加一份配置驱动的规则表 `naming-config.example.json`。

`SKILL.md` 里定了这些事：信息来源与采信门槛、命名格式细则、目录规则、字幕策略、七步工作流程、Dry Run 的强制要求、冲突与不确定信息怎么处理、以及禁止操作清单。

可调的项都外置在配置里，比如：

```jsonc
{
  "defaults": {
    "titleRule": "chinese-first",          // 中文译名优先
    "zhTitleAcceptance": {                  // 「中文剧名」的第二源门槛
      "appliesTo": ["zh-drama-title"],
      "otherwiseMinAgreeingSources": 2
    },
    "episodeTitle": {
      "wrapIn": "「」",                     // 集标题用直角引号包裹
      "omitWhenMissing": true               // 无可靠标题则省略整段
    },
    "movie": { "template": "片名 (年份) 分辨率.扩展名" },
    "folderStructure": {
      "singleSeasonNoSeasonFolder": true,   // 单季作品不建季文件夹
      "seasonFolder": { "pattern": "第{n}季" }
    },
    "safety": { "dryRunRequired": true, "neverOverwrite": true, "neverDelete": true }
  }
}
```

### `src/naming/` —— 命名规范化

| 模块 | 职责 |
|---|---|
| `techinfo_reorder.py` | 把技术信息重排成 `来源.分辨率.动态范围.编码.位深.音频.声道`，`H264/H265` 归一到 `H.264/H.265`，并列出被丢弃的发布标记。内置两道保护，挡住「声道号含点号」和「编码含点号」这两个踩过的坑 |

### `src/sources/` —— 数据源适配器

| 模块 | 职责 |
|---|---|
| `tmdb/tmdb_api.py` | TMDB 只读取数：`selftest` / `search tv\|movie` / `tv` / `season` / `movie` / `titles` / `raw`。只发 GET，不写远端数据。密钥只从环境变量或独立文件读，日志里只出现掩码 |

### `src/storage/cd2/` —— 存储后端与执行链路

| 模块 | 职责 |
|---|---|
| `cd2_client.py` | CloudDrive2 gRPC 客户端：列目录、读信息、建目录、改名、移动。不含删除，不含上传下载 |
| `selftest_api.py` | 后端连通性自检，只建目录 / 改名 / 移动，不删任何东西 |
| `v2_plan.py` | 批量生成「机械改造」计划：删技术信息、集标题加引号。不重查标题 |
| `check_plan.py` | 计划体检，揪出被误切进集标题的技术残留 |
| `apply_plan.py` | 计划执行器，默认 dry-run，加 `--apply --yes` 才落盘 |
| `audit_v2.py` | 只读审计，统计已合规 / 待改造的文件数 |
| `snapshot.py` | 名字 + 字节数 + MD5 快照与比对，用来证明「只改名、未动内容」 |
| `probe_tracks.py` | 只读探测容器内轨道（含内封字幕），不下载视频正文 |
| `audit_subs.py` | 只读审计内封字幕，找出真正缺字幕的集 |
| `delete_list.py` | 唯一的删除入口：只接受字幕文件或完全空目录，先列清单、默认 dry-run、走云端回收站 |
| `cleanup_testdirs.py` | 清理自检产生的空目录，死白名单加递归零文件校验 |

## 数据源

数据源用来认作品、取元数据，不参与文件写入。

| 数据源 | 用途 | 状态 |
|---|---|---|
| TMDB | 作品身份、年份、季结构、季名、分集标题、地区别名 | 已实现 |
| 官方平台 / 官方字幕 / 官方发行名 | 中文译名与集标题的权威单源 | 已实现（查证流程） |
| 豆瓣 | 中文译名与集标题的补充来源，尤其中文影视 | 已实现（查证流程） |
| Wikipedia | 中文译名与集标题的补充来源 | 已实现（查证流程） |
| dandanplay 开放 API | 计划中：动漫作品识别与剧集匹配的数据源之一 | 尚未接入，未申请到权限 |

采信门槛按字段分层，不是一刀切：

| 字段 | 门槛 |
|---|---|
| 中文剧名 | 主来源给出中文名之后，还要 1 个独立来源印证（官方来源可直接采信）；否则退回官方原名 |
| 年份 / 季结构 / 季名 / 集标题 | 主来源单源即可采用 |

同一个数据源内部的多语言变体不算两个来源。TMDB 的 `zh-CN` 和 `zh-TW` 同属 TMDB，互相印证不了。

数据源可以按媒体类别区分主来源（比如动漫和剧集用不同的），但这是换**来源**，不是换**命名规则** —— 命名格式始终全库统一。

## Dandanplay 用在哪一步

dandanplay 开放 API **计划**作为本项目**动漫**媒体识别与剧集匹配的**数据源之一**，辅助确定动漫作品和具体剧集。

动漫是最需要额外判断依据的类别。同一部动漫在不同资料库里可能对应不同的别名和译名，季集划分也常不一致；下游按名字匹配时，一旦拿到的季集编号跟自己的口径不符，就会匹配到错误的剧集。多一路动漫向的来源做交叉验证，能降低识别和季集判定出错的概率。

它计划服务于两个环节：

1. **动漫作品识别** —— 从杂乱的动漫文件命名里定位作品身份，含中文名与原始名。
2. **剧集匹配** —— 确定某集属于哪一季、第几集，辅助确认季集结构与分集标题。

接入后只动动漫这一类：动漫的主数据源从 TMDB 换成 dandanplay，TMDB / 豆瓣 / 维基降为补充来源。其余类别（剧集、电影、纪录片、综艺）的规则不变。中文剧名的第二源门槛不因为换源而取消。

当前状态，免得误会：

- 本项目**尚未**获得 dandanplay API 权限，**没有**任何 AppId / AppSecret / API Key；
- 仓库里**不含** dandanplay 的调用代码，也**不含**任何调用结果；
- dandanplay **不是**本项目的驱动者，本项目**不是**它的客户端，也不是替代品；
- 它就是一个可选的数据源适配位，与其他数据源地位相同，只覆盖动漫这一类。

相应地，dandanplay 的弹幕数据、播放器功能、账号体系、社区功能，本项目不包含，也不计划包含。

## 怎么用

下面写的都是**当前真能跑**的用法。

### 环境要求

- Python 3.11+（`tomllib` 依赖；`src/storage/cd2/` 另需 `grpcio` 和 `protobuf`）
- 媒体库放在本地目录、Alist 挂载盘，或者通过 CloudDrive2 / 网盘 MCP 访问都可以

### 1. 作为 Skill 用（推荐）

把 `skills/media-library-auto-rename/` 作为 Skill 载入，复制一份配置改成自己要用的规则，然后让助手按 `SKILL.md` 的流程走：

```text
扫描目录 → 建立视频—字幕对应 → 识别作品 → 查询数据源 → 确定集标题
        → 读取技术信息 → 生成计划 → Dry Run 待确认 → 执行 → 校验
```

没有明确确认，不会落盘。

### 2. 命令行

**技术信息字段规范化**（零依赖，自带自测）：

```bash
python src/naming/techinfo_reorder.py
```

**TMDB 数据源**：

```bash
python src/sources/tmdb/tmdb_api.py selftest                     # 自检：密钥 / DoH / 连通 / 查询 / 占位识别
python src/sources/tmdb/tmdb_api.py search tv "剧名"              # 搜剧，拿候选 id
python src/sources/tmdb/tmdb_api.py tv <id>                      # 季结构表
python src/sources/tmdb/tmdb_api.py season <id> <季号>            # 该季全部集标题（中英对照，自动标注占位）
python src/sources/tmdb/tmdb_api.py movie <id>                   # 电影详情
python src/sources/tmdb/tmdb_api.py titles tv <id>               # 别名与地区译名
```

密钥从环境变量 `TMDB_API_KEY` 或 `~/.config/media-nomenclator/tmdb_api_key` 读取，不会写进仓库，也不会打到日志里。

**CloudDrive2 后端**：

```bash
cd src/storage/cd2
python selftest_api.py                                    # 后端连通性自检
python v2_plan.py --root /media/tv/shows --out plans/tv.json   # 生成计划
python check_plan.py "plans/*.json"                       # 计划体检
python apply_plan.py plans/tv.json                        # dry-run（默认，不落盘）
python apply_plan.py plans/tv.json --apply --yes --verify  # 执行 + 校验
python snapshot.py --plan plans/tv.json --save baseline.json   # 存内容快照
python snapshot.py --plan plans/tv.json --diff baseline.json   # 比对：内容是否零改动
```

令牌从环境变量 `CD2_API_TOKEN` 或 `~/.config/media-nomenclator/cd2_token` 读取。

### 3. 计划文件格式

见 `examples/rename-plan.example.json`。计划只支持三种动作：`mkdir`、`rename`、`move`。

## 动手之前的安全设计

这套工具会动真实文件，所以安全性优先于功能多少。

| 机制 | 说明 |
|---|---|
| Dry Run 强制 | 执行器默认只打印，必须显式 `--apply --yes` 才落盘 |
| 绝不覆盖 | 目标已存在就是 `SKIPPED_CONFLICT`，保留原文件并报告；移动操作的冲突策略固定为 skip |
| 绝不猜 | 无法可靠确认的项标 `NEED_REVIEW`，保持原样 |
| 不删除 | 通用客户端和执行器不含删除能力。删除被隔离在一个独立脚本里，只接受字幕或空目录，先列清单、默认 dry-run、走回收站 |
| 不改内容 | 只改文件名，不转码、不剪辑、不动字幕内容和时间轴 |
| 路径护栏 | 云端执行链拒绝任何带盘符、反斜杠或 UNC 的路径，从源头保证不会误操作挂载盘 |
| 幂等重试 | 已完成的条目重跑会自动跳过，限流类错误带退避重试 |
| 完整性证明 | 快照比对（名字 + 字节数 + MD5）证明只改名、未动内容 |
| 密钥不外泄 | 所有密钥只从环境变量或独立文件读取，不入仓库、不入配置，日志里只有掩码 |
| 分批执行 | 大批量拆成小批次，不容易触发限流，也方便随时中断复核 |
